# Can soil, weather and location features be added to the price model? (feasibility check, 2026-10-27)

Nothing here changed the production model, the database or any dataset. Everything below was read from the files and from the earlier
weather evaluation in `dataset/reports/weather_eval/`.

## What the production price model uses (29 inputs, from `price_preprocessing.joblib`)

Price history (latest price, 1/3/7/14/30-day changes, rolling-average gaps, volatility, momentum), price spread, market arrivals,
the gap to the state median price, season/month/week/day, the crop, market and variety codes, the forecast distance (days) and the
calendar position of the target day. **No weather, soil or coordinates.** The code can accept six weather features, but the deployed
model was trained without them.

## Candidate features and whether reliable historical data exists

| Feature | Data found in the project | Can it be joined to historical price rows? | Verdict |
|---|---|---|---|
| Temperature, rainfall, humidity | Open-Meteo archive (ERA5 reanalysis), downloaded for the mapped markets with enough price history, 2015-2025, in `dataset/weather/` | Yes, by market town and date | Available; **tested, no meaningful gain** (below) |
| N, P, K, pH | `Crop_recommendation.csv` (2,200 rows, 22 crops), `maharashtra_crop_recommendation.csv` (4,550 rows), `crop_dataset_extended.csv` (8,400 rows) | **No.** No date, no market, no observation location. The Maharashtra file was generated by a script (seed 42) from assumed ranges per crop; the extended file adds 3,850 synthetic rows. README 6.2: "not measured on real farms". | **Not usable.** Treating these numbers as measured soil values for historical markets would be fabrication |
| Soil type | `crop_dataset_extended.csv` has a `soil_type` column | No. The 4,550 original rows have `unknown`; the rest are synthetic. It is a label on a recommendation row, not a map of a market's soil | **Not usable** |
| Location | Market names, town centres in `market_locations.csv` (166 mapped, 121 not found, 10 ambiguous) | Yes, but a market town is where produce is *sold*, not where it is *grown* | Market identity is already a model input (`market_code`); coordinates add nothing the code does not already carry. The farmer's growing location is not in any price record |
| Arrivals, min/max, modal price | The price file | Yes | Already used |

A reliable soil source would need real, location-specific measurements (for example government soil-health-card data by district or block)
with dates, and a documented way to link a growing district to the market its produce is sold in. None exists in the project.

## Weather result already measured (do not re-run)

Same model with and without six weather features, trained on earlier data and scored on the unseen 2025 Q3 and Q4 test months
(800,000 cases): overall MAE 438.7 without weather, 439.0 with it. Per crop the change was between 2.7% better (Cabbage) and 1.5% worse
(Onion). Differences of this size are within the evaluation's own noise, so weather is **not** recommended as a model input.

## Conclusion

* No candidate model with soil (N, P, K, pH, soil type) can be trained honestly: there is no real, dated, location-matched data.
* Weather has real data but did not improve the model, so the production model stays unchanged.
* Weather is shown only as background information; soil values are shown as "Not available".
* To revisit: obtain real soil measurements by location and date, then repeat the same chronological evaluation.
